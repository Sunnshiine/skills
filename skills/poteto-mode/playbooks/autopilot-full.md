### Autopilot-full

**You own the verdicts, never the PRs. One owner carries each PR from build to merge, and nothing merges until your swarm, which never wrote the code, has proven the code that lands.**

**Sunny, the operator, has given you full permission to squash and merge.** Running this playbook is the grant. It covers each queue PR that steps 4 and 5 clear, and its owner squash-merges it without asking first. Copy this grant into every owner's brief, because an owner reads only its brief.

A verdict covers one patch and green CI covers one head. Step 4 runs a full swarm once, and again only for a major change. A `catchup carry` of `carry`, per `playbooks/shipping.md` step 3, keeps a lane's result, and every new head needs its own green CI.

1. **The operator's gates come first.** The grant covers only the queue's items, so items the operator names as theirs and PRs outside the queue stop at merge-ready. A request to state the plan is not a go.
2. **Spawn one owner per PR, and keep its work where a replacement can find it.** Resolve the forge once for the program. GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr` for every PR operation. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). Each owner is a fresh worker in its own worktree (a launched thread in T3, per `references/t3.md`) that builds, opens its PR per `playbooks/opening-a-pr.md`, proves the change on the real artifact, babysits to green per `playbooks/babysit.md`, and merges once steps 4 and 5 clear it.

   Open the PR early so CI and bots run alongside the work. The code is ready only after the slop-strip (`/deslop`) and the `/no-comments` pass, so the full swarm runs on finished code. Report the code-ready head before self-proof, every later head, and merge-ready once self-proof, CI, and babysit are done. Rebase only when `~/.claude/skills/poteto-mode/scripts/catchup check <head>` says `rebase` or `rerecord-snapshots`, or CI fails from a change on trunk, because each rebase restarts CI. Run the repo's checks for the touched paths on the committed head before the code-ready push and before a later push that needs a verifier.

   Assume the owner's session dies. Soon after starting, push and start a decision trail in the root's `notes.md` per the **show-me-your-work** skill, then push each finished unit before you start the next. Whoever spawns a subagent records its id, state, and a stuck-after runtime from past runs of its kind in that `notes.md`, so the root can probe it if the parent dies. Force-push only your own branch, with `--force-with-lease` pinned to the SHA you last pushed or took over, and on any push you did not make, stop and report to the root.
3. **Run owners in parallel off trunk, never stacked,** so each PR lands on its own.
4. **Swarm-verify once.** A full swarm runs once, at the code-ready head. Another full swarm runs only for new behavior, a redesign, or a large new diff. A rebase keeps its verdict with no verifier when `~/.claude/skills/poteto-mode/scripts/catchup carry <verdict-sha> <new-sha>` says `carry`, and the carried verdict cites its `proof` line. A rebase that says `reverify` gets a single verifier scoped to the `changed` files, a minor fix gets a single verifier at the new head, and a wording-only change gets none. Fan out independent verifiers at the code-ready SHA per the **swarm** skill. They re-run the gates, prove the load-bearing behavior live on the real surface through its control skill (`control-ui` or `control-cli`, see **Harness** in SKILL.md) or a named driver, and audit the diff. The verdict is not clean without the live lane, or before you audit the merge-ready report's receipts, because no lane trusts a claim it has not checked.

   Block a PR only for a problem you can show, with a failing run at the head or a doc line the PR made wrong. A problem the PR's base already has, whether trunk or the PR below it in a stack, doesn't block unless the PR copies it or newly reaches it. Only a bug a user would hit, a failed gate, or a wrong shipped doc blocks, and everything else goes in a follow-up.
5. **The owner merges only what you verified, tested on the trunk it lands on.** Green CI alone never authorizes a merge, and landing makes no new head. Right before merging, run `~/.claude/skills/poteto-mode/scripts/catchup check <head>`, which fetches trunk, and record the SHA on its `base` line. On `none`, build and run the patch's checks on the merge result in a scratch worktree of that trunk SHA with the head merged in. Merge on a pass if trunk still has that SHA, and check again if it moved. `gh pr merge` cannot pin the base, so trunk can still move between that last check and the merge. When the squash commit's parent is not the recorded SHA, rerun this step's check on the new trunk and report a failure to the root as a trunk break. On `rebase` or `rerecord-snapshots`, or when the merge result fails where the head passes, rebase, report the new head, and wait for green CI and step 4. On a third trunk move or a third rebase, hold and report to the root, which sequences the colliding work.
6. **Run the root layer.** After each merge, run `~/.claude/skills/poteto-mode/scripts/catchup radar <open heads>` and message only the owners on its `rebase`, `rerecord-snapshots`, and `pair` lines. Never hold every owner for one merge. Anything that loosens a gate, such as a raised budget or an allowlist entry, needs a verifier's proof and then your fresh countersign, because the owner is the one who wants green. Under a grant that covers approvals, that countersign is the approval, and the owner's record of it points at your countersign for a lane to check. A disabled or soft-failed check always comes out, because it stops guarding every case. Never give or bypass an approval the forge enforces, because no countersign covers it.

   On the operator's go, arm an hourly `/loop` (see **Harness** in SKILL.md) to audit until no delegated work is left, because long runs drift and agents stall silently. Each tick re-reads this playbook from trunk and fixes drift, such as an unreported head or an unrecorded agent, by having its owner record it, because drift is a gap in the record, not a stall. It probes every agent, down to the leaf lanes, and judges each by its side effects, because status text and summaries can hide a stuck child. An agent is stuck when it errors, cannot start turns, or shows nothing new past its stuck-after runtime, and so is an owner that has neither pushed nor written a trail row by the first tick. One waiting on you or the operator is not stuck, so answer it. Replace a stuck agent at once, without waiting for its stop to land. A tick that changed something for the operator ends by catching them up per the **ketchup** skill, and one that changed nothing stays quiet.
7. **Stand down at once on the operator's stop.** A hold reaches every owner as a zero-writes order. Each reports where it stands and keeps its brief until the operator releases it.

**Reply:** catch the operator up per the **ketchup** skill, covering each PR's state and verdict, what merged, countersigns and why, open operator gates, and parked follow-ups, with links to each PR and the trails.
